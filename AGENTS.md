# AGENTS.md

FinTrak: personal finance tracker. Monorepo with `backend/` (Go 1.27 + Gin + PostgreSQL/pgx) and `frontend/` (React 19 + TypeScript + Vite + Tailwind CSS 4, managed with bun). All routes live under `/api/v1`; the human-readable API overview is in `README.md` and the machine-readable spec is `backend/openapi.yaml` (kept in lockstep by a route-parity test).

## Commands (run from repo root)

- `make dev` — `docker compose up -d` (db + statement-parser + backend + frontend + adminer). Frontend at :3000, API at :8080, parser at :5000, adminer at :8081 (the dozzle log viewer is behind the `debug` profile). Every published dev port is bound to `127.0.0.1`, so the dev stack is host-only. The dev and production Compose files are separate projects (`fintrak-dev` / `fintrak-prod`) with separate volumes, so they cannot adopt each other's database. `make dev-down` stops it.
- `make test` / `make test-cover` (backend coverage profile) / `make test-cover-check` (enforces the 85% floor) / `make test-integration` (backend, Docker + testcontainers) / `make test-parser` / `make test-parser-cover-check` (enforces the 90% parser floor) / `make test-client` / `make test-client-cover-check` (enforces the 85% client floor) / `make test-tui` / `make test-tui-cover` / `make test-tui-cover-check` (enforces the 18% TUI floor) / `make test-mcp` / `make test-mcp-cover-check` (enforces the 80% MCP floor) / `make vet` / `make vet-client` / `make vet-tui` / `make vet-mcp` / `make build-backend` / `make build-frontend` / `make build-client` / `make build-tui` / `make build-mcp` / `make openapi-check`. `make prod` / `make prod-no-db` / `make prod-down` manage the production stacks.
- `make release VERSION=v1.2.3` — must be on `master` at `origin/master` with a clean tree; runs the same gate CI's `validate` job does, through the same entry points: per Go module `go mod tidy` + `git diff --exit-code go.mod go.sum`, `make vet vet-client vet-tui vet-mcp`, `uv lock --check`, `make test-cover-check test-client-cover-check test-tui-cover-check test-mcp-cover-check test-parser-cover-check openapi-check test-integration`, `bun install --frozen-lockfile`, `bun run typecheck`, `bun run test:coverage`, `bun run build` — then tags & pushes. CI then publishes GHCR images. Releases are only cut from `master`. Because the gate is the Makefile's, the coverage floors and the release gate cannot drift apart; a regression that CI would reject fails before the tag exists.
- Frontend scripts: `dev`, `build`, `preview`, `test` (vitest), `test:watch`, `test:coverage` (v8, with an enforced regression floor), `typecheck` (`tsc --noEmit`). Verification is `bun run build` + `bun run test` + `bun run typecheck`. Install deps with `bun install` (lockfile is `bun.lock`).
- CI (`.github/workflows/docker-publish.yml`) also enforces `go mod tidy` leaves `go.mod`/`go.sum` unchanged — keep them tidy. The frontend CI job uses `oven-sh/setup-bun` (pinned to the Dockerfile's Bun version) and runs `bun install --frozen-lockfile`, `bun run typecheck`, and `bun run test:coverage`; backend, frontend, parser, and tui coverage profiles are uploaded as build artifacts. An aggregate `validate` job requires all test jobs (including `test-backend-integration`) and every `publish-*` job `needs: [validate]`, so a tag cannot publish a partial release.

## Backend

- All routes are registered in `backend/main.go` `setupRouter` (per-handler groups). Adding an endpoint means: handler in `handlers/`, route in `main.go`, migration if schema changes.
- All models/types live in one file: `backend/models/models.go`. Handler filenames are named after the resource they own and use the singular form where it applies: `rule.go`, `link.go`, `payee.go`, `account_type.go` (multi-word concerns stay together, e.g. `transaction_bulk.go`, `billing_cycle.go`).
- **Migrations**: never edit the schema directly. Add a new `NNNNNN_*.up.sql` / `.down.sql` in `backend/db/migrations` (the base schema is a squashed migration, `000001_initial_schema`; later migrations alter it). Migrations run automatically at startup via `db.RunMigrations`, followed by the idempotent every-boot seeders `db.SeedAccountTypes()` and `db.SeedCategoryGroups()`. `SeedDefaultCategories` runs per-user inside the registration transaction.
- **Tests need no database**: handlers take their dependencies from an explicit `handlers.Server` (constructed with `handlers.NewServer(pool, parserURL, logBodyLimit)`), so unit tests build a `Server` over a `pgxmock` pool (see `handlers/testhelpers_test.go` `newTestServer`/`newMockServer`) instead of swapping a package global. The `db` package's own tests still use `setupMock` (`backend/db/db_test.go`). Tests that hit SQL expect exact queries/args against the mock — change a query string or arg order and tests fail. Follow the existing `new*TestRouter()` + `testAuthMiddleware()` helpers; always call `gin.SetMode(gin.TestMode)`.
- **Integration tests are opt-in and Docker-backed**: `backend/integration_test.go` (build tag `integration`, `package main`) boots the real Gin router against a throwaway PostgreSQL container via testcontainers (`go test -tags=integration ./...`, or `make test-integration`). It applies migrations through the error-returning `db.Migrate` (startup still uses `db.RunMigrations`, which wraps it and `os.Exit`s on failure), then exercises auth, import dedupe (including concurrent skip imports), concurrent link creation, cross-account billing-cycle rejection, PATCH-to-loan rejection, link-delete category semantics, and billing-cycle generation end to end. The default `go test ./...` stays database-free.
- Config via godotenv (`.env`, template in `.env.example`). `APP_ENV` accepts only `development` or `production`, and an unset or empty value means `production` (fail closed): the built-in development secrets are reachable only from an explicit `APP_ENV=development`. Outside explicit development, startup fails unless both `JWT_SECRET` and `TOKEN_ENCRYPTION_KEY` are set, are none of the development values this repository publishes (`publishedDevSecrets`), and pass a 32-character/non-repetitive strength floor; the session cookie defaults to `Secure`. `ALLOWED_ORIGINS` is a comma-separated CORS allowlist and `TRUSTED_PROXIES` is a comma-separated proxy-CIDR allowlist for forwarded client-IP headers (empty trusts none, so `X-Forwarded-For` cannot be spoofed; the production Compose files default it to the frontend nginx's single static `app-net` address — `FRONTEND_IP`, `172.28.0.2/32` — rather than the subnet, because gin believes the left-most forwarded entry whenever the peer is trusted and the unauthenticated statement parser shares that network, so a subnet-wide allowlist would let it forge a client IP and pick its own rate-limit bucket). `LOG_BODY_LIMIT` <= 0 disables debug request/response body capture. `main.Version` is injected via `-ldflags` in Docker builds.
- Business logic stays in handlers; e.g. transfer scoring is `calculateTransferScore` in `backend/handlers/link.go`.
- **Money**: amounts are stored and computed as integer minor units (cents) via `backend/internal/money.Amount` (an `int64`); `transactions.amount` is `BIGINT` cents. `money.Amount` marshals/unmarshals as decimal major units at the JSON boundary (so the API still speaks dollars) and implements `sql.Scanner`/`driver.Valuer` for the BIGINT columns. Never do money arithmetic in `float64`; use `money.Parse`/`FromFloat` at input edges and `.String()`/`.Float64()` only for display. Every boundary conversion is bounded by `money.MaxMinorUnits` (`1<<62`, exactly representable as a float64): `Parse`, `UnmarshalJSON` and the `float64` branch of `Scan` reject a non-finite or out-of-range value with an error instead of wrapping it into the int64, because a wrapped value marshals as a malformed JSON number and makes *every* response containing that row fail. `Parse`'s grammar is one optional leading sign, digits on both sides of the point, at most two fraction digits — `"."`, `"-"`, `".5"`, `"5."` and `"--1"` are errors, not zeroes. `client/api.ParseAmount` mirrors that grammar, so a client cannot submit what the API would refuse.
- **Sessions are recorded server-side**: `POST /auth/refresh` rotates the refresh cookie and `refresh_tokens` (migration `000012_refresh_tokens`) keeps one row per issued token (SHA-256 only) grouped into a rotation `family_id`. Presenting an already-rotated token is treated as **reuse** and revokes the whole family; `POST /auth/logout` revokes the family too. Do not describe the refresh token as stateless, and do not add a code path that mints an access token without a live row for the presented refresh token. `POST /auth/login`/`/auth/register` are throttled per client IP only (a per-identity budget exists but is charged solely for *failed* credentials, so it can never lock a real user out) and cap the request body at 4 KiB.
- **Dates have a window**: every write edge that accepts a transaction date goes through `validation.CheckTransactionDate` (`[1900-01-01, today+1y]`, `backend/internal/validation/date.go`), and `billingCycleMonths` clamps its own span. Without both, one typo'd year makes `ensureBillingCycles` emit one INSERT per month back to year 1 on every read of that account.
- **`transactions.tags` is never NULL**: the write edges bind `[]string{}` and every reader uses `COALESCE(t.tags, '{}')`. A NULL breaks `unnest(tags || $2::text[])` (so a bulk tag add silently stores nothing) and serializes as `"tags": null` where the spec promises an array.
- **`billing_cycle_id` follows the date, unless the user said otherwise**: a date or account move clears it, an explicit `billingCycleId: null` clears it durably (`transactions.billing_cycle_detached` keeps `ensureBillingCycles`' back-fill from re-attaching it), and naming a cycle always wins.
- **Some `GET`s write**: the billing-cycle generation on `/accounts/{id}/billing-cycles`, `/transactions`, the dashboard aggregates (`/dashboard/summary`, `/dashboard/money-flow/timeline`, `/dashboard/cash-flow-calendar`) and the legacy-token re-seal on `/paperless/documents`. Because a `SameSite=Lax` cookie rides a cross-site top-level navigation, `crossSiteGetGuard` refuses those routes — plus `/accounts/{id}/export`, a pure read that a cross-site navigation must not silently download — when the request declares `Sec-Fetch-Site: cross-site` (same-origin and header-less clients are unaffected). The guard's list is about the cookie, not about writing: a *writing* GET also belongs in `mcp/internal/readonly.SideEffectingGETs` with a `SideEffect` on its tools, while a pure read does not.
- **Logging**: use `log/slog` with typed attr helpers — `slog.String`/`slog.Int`/`slog.Bool`/`slog.Duration`, and `slog.String("error", err.Error())` (or `slog.Any` when the value is not statically an `error`, e.g. a recovered panic). Do not use the bare key/value form (`slog.Error("...", "error", err)`).
- Statement parsing (`backend/handlers/statement.go`) is decoupled: the backend only forwards uploaded PDFs to a standalone Python service (`statement_parser/`) over HTTP. The parser base URL comes from `STATEMENT_PARSER_URL` (config `ParserURL`, passed to `handlers.NewServer` in `setupRouter`). A `Server`-level semaphore (`maxConcurrentParses`) caps concurrent forwards and returns 429 when saturated. Handler tests use `httptest` to simulate the upstream parser. `forwardStatementToParser` is the shared helper that wraps the PDF into multipart and forwards it — reused by both the manual upload path (`ParseStatement`) and the Paperless import path.
- Paperless-ngx integration (`backend/handlers/paperless.go`) stores per-user settings (`paperless_url`, `paperless_token` columns on `users`) — not docker/env. Config is set via the Settings UI; the Paperless import UI (`frontend/src/components/PaperlessImport/`) is hidden until both fields are set. `ListPaperlessDocuments` proxies `GET /api/documents/`, `ImportPaperlessDocument` fetches `GET /api/documents/{id}/download/` then calls `forwardStatementToParser`. Handler tests use `pgxmock` for the settings row + `httptest` for the upstream Paperless and parser servers.

## Frontend

- All API calls go through the single `src/api/client.ts` (exports a default `api` object plus `downloadCSV`, `getStoredUser`, `storeUser`). Base URL is `VITE_API_URL` or defaults to `/api/v1` (same-origin); the Vite dev server proxies `/api` to `http://localhost:8080`. Do not call `fetch` elsewhere.
- Components are PascalCase directories under `src/components/<Feature>/<Feature>.tsx` (e.g. `Dashboard/Dashboard.tsx`, `Transactions/Transactions.tsx`). Routing is in `src/App.tsx`; entry point is `src/main.tsx`. All source is TypeScript (`.ts`/`.tsx`); API models live in `src/types.ts`.
- Global state via React Context in `src/context/` — `AuthContext` (auth state; caches only the non-sensitive user object in localStorage under `fintrak_user` — the JWT lives in an httpOnly cookie), `SettingsContext` (compact layout, page size), `ThemeContext` (light/dark mode + accent theme), and `DomainDataContext` (shared read-mostly lookups — accounts, account types, categories, groups, payees, settings — with per-resource `errors`). New UI should respect the Compact Layout toggle.
- UI is built on **shadcn/ui** (Radix) with primitives in `src/components/ui/`. Config lives in `components.json`; the `@/*` → `./src/*` alias is set in `tsconfig.json`, `vite.config.ts`, **and** `vitest.config.ts` (vitest does not inherit the Vite alias). The `cn` helper is `src/lib/utils.ts`. Add new primitives with `bunx shadcn@latest add <name>` (base: radix); never hand-roll buttons/inputs/modals/selects/tables when a shadcn primitive exists.
- **Theming**: light/dark + 6 accent themes (cyan default, violet, emerald, amber, rose, zinc), all driven by CSS variables in `src/index.css` (`:root`, `.dark`, and `:root[data-theme=…]` / `.dark[data-theme=…]` accent overrides). `ThemeContext` exposes `mode`/`accent`/`isDark` + `setMode`/`setAccent`, persists to `fintrak_theme` in localStorage, and toggles `.dark` + `data-theme` on `<html>`. An external `public/theme-init.js` (referenced from `index.html` so the production CSP can disallow inline scripts) applies the theme before React mounts (no FOUC). The Theme picker lives in Settings.
- Use **semantic tokens**, never raw palette classes: `bg-background`, `bg-card`, `bg-popover`, `border-border`, `text-foreground`, `text-muted-foreground`, `bg-primary`/`text-primary`/`border-primary/*`, `bg-destructive`/`text-destructive`, `bg-muted`/`bg-accent`, `sidebar-*`, and `chart-1..5` (recharts series use `var(--chart-N)`). Only user-supplied colors (account/category hex) stay as inline `style`.
- Component conventions: destructive confirms → `AlertDialog`; errors → `toast.error` from sonner (the `Toaster` is mounted in `App.tsx`); modals → `Dialog`, right-side drawers → `Sheet` (both mounted by a parent's conditional render using `<X open onOpenChange={(o) => !o && onClose()}>`); text inputs → `Input`, dropdowns → `Select`. Radix `SelectItem` values must never be empty strings — use a sentinel (`"none"`/`"all"`) and map back to `""` in `onValueChange`. Deliberate exceptions: the dense inline `EditableSelect` cells and the bulk-action selects in `Transactions/BulkActionBar.tsx` stay native `<select>`.
- `color-scheme` is set globally via CSS, so native date inputs must not use the old `scheme-dark` utility; use `scheme-light dark:scheme-dark` only where a class-level override is genuinely needed.
- **Dates are local days, never UTC ones.** Build a default "today" with `todayLocalISO()` (`src/lib/dates.ts`, which also owns the shared period-range helpers: the twelve-month window and the April–March financial year) and turn a stored `YYYY-MM-DD` into a `Date` with `parseDateOnly` (`src/utils/formatters.ts`): `new Date().toISOString().split("T")[0]` yields *yesterday* for anyone east of UTC before 05:30, and `new Date("YYYY-MM-DD")` parses as UTC midnight and can render the day before. Inline edits must also PATCH only the field the user changed — a whole-row body silently reverts a concurrent edit.
- Tests run under Vitest + jsdom (`vitest.config.ts`; shared polyfills in `src/test/setup.ts`). `jsdom` is deliberately pinned to `~30.0.1`: 30.1.0 leaves Radix Select popups unable to open once an earlier test in the same file has opened and torn one down (16 interaction tests across 6 files fail with the trigger stuck at `aria-expanded="false"`), so re-run the frontend suite before relaxing the pin.
- CSV import is client-side (PapaParse) in `components/Import/Import.tsx`; bank-statement parsing quirks live there.
- Vite dev server runs on :5173 (`host: true` for Docker). In the Docker/nginx setup the frontend reverse-proxies `/api/v1` to the backend.
- **The app is also an installable PWA, and its offline layer is hand-written.** `public/manifest.webmanifest` + `public/sw.js` (no build plugin: `vite-plugin-pwa` does not accept Vite 8 yet), with `src/lib/serviceWorker.ts` registering the worker in production builds only — it is verified against `bun run preview`, not the dev server, because the dev server has no hashed asset graph and an installed worker would outlive HMR. The worker caches the shell plus the bundles `index.html` names, and never touches `/api/`: authenticated JSON is cached by the app instead, deliberately and per path.
  - **Reads**: `src/api/offlineCache.ts` keeps the last successful GET for an allowlist of paths in `localStorage`, namespaced by user and cleared on sign-out, and `src/api/client.ts` answers a request that never reached the server from it. The owner is captured where the request is *issued* (not re-read from `fintrak_user` when the response lands), so a response that arrives after a session swap is never attributed to the wrong user; `AuthContext` clears the departing user's blob on every sign-out path and a `storage`-event guard reloads a tab whose identity another tab replaced. `src/api/offlineStatus.ts` is the small external store (read with `useSyncExternalStore`) that says whether the browser is online and whether the last read came from the cache; `components/Layout/OfflineBanner.tsx` is the only place that speaks to the user about it.
  - **Writes**: `src/api/outbox.ts` queues manual creates per user; `context/OfflineContext.tsx` flushes them on reconnect, on launch and on demand. **The queue is the source of truth, so the storage write decides what the caller may claim**: `writeEntries` reports whether the write landed, `enqueueCreate` throws rather than resolving a queue entry that does not exist, and a queue already at `MAX_ENTRIES` refuses the new entry instead of evicting the oldest (both are user-recorded money, and silently dropping either is unrecoverable). A flush stops on a transport failure or a 401/5xx (the queue keeps its order) but marks a rejected payload with the server's message so one bad entry cannot block the rest or retry forever; an entry that could not be removed after the server accepted it is reported as `unsaved`, not swallowed.
  - **Never create twice**: `api.createTransaction` always sends a client-generated `clientKey` and queues the same body when the request never reached the server, so the replay the flush performs is recognised by `POST /transactions` (see the backend note above). `ApiError`/`NetworkError` (`src/api/errors.ts`) are what distinguish a rejected request from an unreachable server — a rejected create is surfaced, never queued.
  - **Offline boot must not sign the user out**: `AuthContext` keeps the cached session when the `/auth/me` probe fails with a transport error, so an installed app opened offline shows its cached data (and the banner) rather than the login screen. The pages that show ledger data (Dashboard, Transactions) reload on `syncedAt` from `OfflineContext`, and `src/lib/prefetchRoutes.ts` warms the dashboard/transactions chunks so a fresh install can open them without a network. `nginx.conf` serves `/sw.js` and `/manifest.webmanifest` with `no-cache` and states the security headers once in `frontend/security-headers.conf`, which every location that sets its own `Cache-Control` includes (nginx stops inheriting `add_header` there); no CSP change was needed (`manifest-src`/`worker-src` fall back to `default-src`/`script-src 'self'`).

## Shared API client (`client/`)

The hand-written Go client for the REST API, in its own module `github.com/fintrak/client` (package `client/api`) so the two Go clients use one client rather than a copy each: `tui/` and `mcp/` both `require` it with a `replace => ../client`. It is a **pure client** of the same API the SPA uses — no backend endpoint exists for it.

- **Why a module and not `tui/internal/api`**: `internal/` is importable only inside the module that owns it, so the MCP server could not have reused the client from another module. Extracting it kept one client; copying it would have produced a second auth/refresh/filter implementation with no drift guard.
- **Because the module is local-path replaced, the image builds that use it need a root build context.** `tui/Dockerfile` is built with `context: .` + `file: tui/Dockerfile` (CI's `build-images` matrix and `docker-compose.yml` both say so), and the root `.dockerignore` keeps that context small — and keeps `.env`/`.env.*` (the production secrets) out of it, since a remote buildx builder receives the whole context — Docker sends the context verbatim and only `.dockerignore` applies, not `.gitignore`.
- **Auth** lives here: no `net/http/cookiejar`. The jar honours the `Secure` attribute on send, so against `COOKIE_SECURE=true` it silently drops the session cookies over plain HTTP; the client parses `Set-Cookie` on every response, attaches `fintrak_token` explicitly (and `fintrak_refresh` only to `/auth/refresh`), and replays a request once after a single-flight refresh on 401. Credential-carrying endpoints (`/auth/login`, `/auth/register`) go out with `withoutAuth()`, so a 401 there reports the server's own message instead of "session expired".
- **Money is never computed.** `api.Amount` carries the decimal text the API sent; `Display()`/`signedAmount()` format it, `ParseAmount` mirrors `money.Parse` at input edges, and `Float64()` is display-only (bar widths) and documented as such.
- **Drift guard**: `api/spec_parity_test.go` holds one `routeCase` per operation, each making a real call to a client method. `TestRouteTableMatchesTheSpec` compares it against `backend/openapi.yaml` (at `../../backend/openapi.yaml`) in both directions, and `TestEveryRouteHitsItsDocumentedPath` executes every case against a stub asserting method, path and query. **Adding a backend route fails the suite until the client claims it**, and a renamed method fails the build.
- **`api.SetTransport`** is the hook for a request policy: the MCP server installs its read-only guard through it. A nil transport restores the default.
- Its own floor (`make test-client-cover-check`, CI job `test-client`, Codecov flag `client` at 85%) because it is its own module.

## Terminal client (`tui/`)

A second frontend: a Go + Bubble Tea client that talks to the same REST API. It is a **pure client** — no backend endpoint exists for it, no schema change, and it inherited all 92 routes without touching `backend/`.

- **Separate module** `github.com/fintrak/tui` at top level, mirroring `statement_parser/`, deliberately *not* `backend/cmd/`: `make test-cover-check` enforces an aggregate 85% floor over `backend/ ./...` and `cmd/covercheck` excludes only each command's own `func main()` (derived from the source), so render-heavy UI code would drag that gate down and couple two release cadences. The TUI carries its own floor instead — `make test-tui-cover-check`, and the matching `Enforce coverage floor` step in the CI job, run the same stdlib-only `cmd/covercheck` against `tui/coverage.out` at 18% — and reports under its own Codecov flag (`tui`, target 18%). The number is lower than it was (25.25% → 19.77%) because the shared API client moved to `client/`: it supplied most of this module's covered statements and now carries its own 85% floor, so the TUI's number measures the terminal client alone.
- **The API client lives in the shared `client/` module** (see above); the TUI imports `github.com/fintrak/client/api`.
- **The one live test is opt-in**: `internal/sshd/zz_real_test.go` drives the SSH door against a real API and skips unless `FINTRAK_REAL_API_URL` is set (`FINTRAK_REAL_API_URL=http://localhost:8080/api/v1 go test -run TestZZRealAPI ./internal/sshd`). CI has no API, so it must never run ungated — every other TUI test builds its own `httptest` stub.
- **Screens** live in `internal/ui` (13 of them: dashboard, transactions, accounts, categories, payees, tags, rules, links, recurring, money flow, calendar, import, settings) and register themselves from `init()` with `registerScreen(order, build)`; `order` is the sidebar position, `screens_test.go` pins the set. Key presses are delivered **only to the visible screen** (a key carries no tag, so broadcasting it would move every screen's cursor and let two screens answer one press); tagged data messages are still broadcast to every screen, so **message tags must be namespaced per screen** (`txn.list`, `accounts.save`, …) — two screens sharing a tag would both react. Screens are created once per session after the reference-data load, so their cursors and filters survive navigation.
- **Optional request fields use `omitzero`, never `omitempty`.** `encoding/json` cannot omit a struct, so an `OptionalUUID`/`OptionalInt` tagged `omitempty` serializes its zero value as an explicit `null` — which the API reads as "clear this column", silently wiping data on an unrelated update. `omitzero` consults the types' `IsZero` method; `client/api/optional_test.go` pins absent/value/null for the real request bodies.
- **Overlays** (form, confirm, picker, info) are owned by the App and opened through `Ctx.Open`; a form closes on its own `done`, or explicitly via `Close()` when its submit performs a local action. `tab` is the App's pane-focus toggle and never reaches a screen — multi-pane screens cycle panes on `p`.
- **Key delivery and the login screen**: while signed out the App hands every message to the login model, because the screen list is empty until the reference data loads. A data message routed to the screens instead leaves the sign-in form stuck (caught by an end-to-end run, pinned by `app_test.go`).
- **Navigation**: `tab` toggles the keyboard between the sidebar and the content pane; the sidebar's arrows browse screens *without* taking focus (moving the selection must never hand the keyboard to the content — that made the sidebar unusable), while a deliberate jump (digit, `[`/`]`, the `g` list) does enter the screen. The status bar advertises the keys that are live in the current pane plus the way back to the other one, and separates its message from those hints. Pinned by `TestSidebarArrowsKeepFocusInTheSidebar`, `TestDeliberateJumpEntersTheScreen` and `TestStatusBarHidesDeadKeys`.
- **SSH door** (`internal/sshd`, `-ssh`): password auth exchanges the SSH credentials for an API session so the session opens signed in; public-key auth only opens the door and the TUI shows its sign-in screen. Forwarding, subsystems and unknown channel requests are refused, sessions are capped, and auth attempts are throttled per remote address — necessary because every session reaches the API from the door's IP and would otherwise share one rate-limit bucket. Passwords are never logged. wish composes middleware so the **last entry is outermost**: the session cap must be listed last to hold its slot for a whole session.
- `tui/Dockerfile` builds the SSH-door image from the **repository root** as its build context (the module replaces `client/` by path); `docker compose --profile tui up -d` starts it on :2222. The image creates `/home/appuser/.config/fintrak-tui` owned by `appuser`, because a named volume mounted there would otherwise be root-owned and the unprivileged process could not write its host key.

## MCP server (`mcp/`)

The read-only agent surface (idea #59) as its own module `github.com/fintrak/mcp`, over the official Go SDK and stdio, so an MCP client launches `fintrak-mcp` as a subprocess. It reuses `client/api`; no backend route, model or migration is involved.

- **Read-only surface** (idea #59): the read-only half of the agent surface, over the official Go SDK and stdio. Every tool declares the API operation it performs (`Tool.Route`) and the registry is the single source of truth for the audit in `tools_test.go`: each route exists in `backend/openapi.yaml` and is a `GET` or one of the two documented preview `POST`s (`/transactions/validate`, `/rules/preview`); every read-only operation is either a tool or listed in `unexposedRoutes` **with a reason**, so a new backend read forces a decision instead of becoming a silent gap; calling every tool through a real MCP session hits exactly the route it declares *with the arguments it declares* (the stub compares the whole query set, and `argumentCases` must cover every tool); and a tool whose route is not a pure read declares what it writes in `Tool.SideEffect`, which is appended to the description the model reads.
- **The read-only promise is enforced, not documented.** `mcp/internal/readonly.Guard` is installed as the client's transport (`api.SetTransport` exists for it), allows the tool routes plus the session routes, and refuses everything else — including the shared client's write methods. The `POST` previews are the only non-`GET` operations admitted; adding one is a claim about the API, so it belongs in `readOnlyPosts` with the audit test as the reviewer. `GET` is not read-only by definition here, for two unrelated reasons: five routes reach `ensureBillingCycles`, which materializes an account's statement periods and back-fills its transactions' cycle assignment, and `GET /paperless/documents` re-seals a legacy-format Paperless token on the user's row. All six are enumerated in `readonly.SideEffectingGETs` with that reason, every tool performing one must carry a `SideEffect` (the audit fails either way round: an undeclared side effect *and* a declared one on a route that is not listed), and the qualification is stated in `mcpserver.go`'s instructions rather than hidden. `Annotations.ReadOnlyHint` is **derived** from `Tool.SideEffect` (`readOnlyHint == (SideEffect == "")`), so a client that auto-approves read-only calls cannot be misled by a stale hardcoded bit; `IdempotentHint` stays true because both writes converge (a repeat finds nothing left to materialize or re-seal). The audit also asserts the *arguments* each tool sends, not just its route. Never add a write tool here without a decision about idea #59's propose-only half.
- **MCP authentication is lazy and above the transport.** Credentials come from `FINTRAK_EMAIL`/`FINTRAK_PASSWORD` (or a token pair), and `mcp/internal/mcpserver` signs in from a receiving middleware on the first `tools/call` — deliberately *not* from a `RoundTripper`: a transport sees a request whose session cookie was attached before the login, so signing in there sends the first call unauthenticated and pays for a 401 replay. The middleware signs in only for `tools/call`, so `tools/list` works with bad credentials, and a failed sign-in is returned as a **tool error** (the model can report it) rather than a protocol error.
- The MCP binary must never write to stdout — that is the protocol channel. Logs go to stderr (`-log-file` to redirect). `mcp/main_test.go` re-executes the test binary as the real server (`FINTRAK_MCP_TEST_MAIN`) and drives it with `mcp.CommandTransport`, which is what pins the sign-in ordering above.
